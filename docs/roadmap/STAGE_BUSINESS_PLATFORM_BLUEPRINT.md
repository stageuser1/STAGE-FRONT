# STAGE 业务平台蓝图 v2（B 轨精简版：私域增长优先）

**日期：** 2026-07-28 · **版本：** v2，**整体取代 v1**（v1 的 Core 身份系统方案降级为"未来触发后再启用的预案"，见 §6）
**性质：** 战略蓝图，非实施规格
**与 T 轨关系：** 不变——`STAGE_VISUAL_REPLACEMENT_PLAN.md`（T0–T7）优先，B 轨不减速、不改道 T 轨。

---

## 0. v2 的核心认知修正

v1 的全部复杂度都源自一个隐含假设：**Lab 需要授权门禁**。业主已裁定 Lab 现阶段是免费获客产品——没有门禁，就没有权益裁决；没有权益裁决，就不需要账号、不需要微信身份映射、不需要回调、不需要 Core。整层砍掉。

**当前阶段的唯一业务问题是：网站访客能不能变成微信私域成员，以及这条漏斗漏在哪。** 架构只需要支撑回答这个问题。

## 1. 三种模型的评估

| | Model A（v1 完整身份系统） | Model B（纯私域引流） | Model C（混合轻量） |
|---|---|---|---|
| 结构 | 匿名层 + STAGE 账号 + 微信映射 + 权益 + 回调 | 网站匿名使用 → 扫码进群 → 人工/半自动运营 | B + 匿名访客 ID + 最小漏斗计量 |
| 复杂度 | 一个新后端服务、境内回调端点、ICP、PIPL 全套 | ≈ 零新后端 | 零~一个极小端点 |
| 现在的收益 | 跨设备同步、可撤销权益——**当前均无对应业务需求** | 完整实现获客目标 | B 的收益 + 知道漏斗是否有效 |
| 运营成本 | 低（自动化）但建设成本高、外部审批周期长 | 线性人工，数千人以下完全可承受 | 同 B |
| 扩展性 | 最好，但为尚不存在的负载付费 | 群活码自动换群可到数千人；瓶颈是人工 | 同 B；且留好了升级到 A 的数据地基 |
| 结论 | **推迟**（§6 触发条件） | 可行，但对"漏斗在哪漏"完全失明 | **✅ 采纳：这就是 MVP** |

**裁决：采纳 Model C = Model B 的漏斗 + 刚好够用的计量。** 判断依据：B 和 C 建设成本几乎相同，但 C 能回答"增长假设是否成立"，而这正是当前阶段（产品验证期）的全部意义。

## 2. v2 架构（全景）

```
  学生/家长 ──► STAGE Customer Platform（现站，T 轨产出，本地优先匿名使用——不变）
                    │
                    │ 唯一新增触点：社群引导卡（群活码二维码 + 进群价值说明）
                    │ 出现在高意愿时刻：首次交卷后 / 复盘页 / Lab 总览横幅（可关闭）
                    ▼
              企业微信客户群（群活码，自动换群）
                    │
                    │ 社群关系与用户沟通 100% 留在微信侧
                    ▼
              员工用企微自带能力运营：标签 = 用户画像，群发/欢迎语 = 触达，
              后台报表 = 社群人数。 ——企微控制台就是 Staff 界面的一部分

  计量面（与上面完全解耦，坏了也不影响任何用户体验）：
  站点流量/页面热度 → Vercel Web Analytics（零建设：最受关注院校 = 按路由的 PV）
  漏斗业务事件（≤8 种）→ 匿名访客 ID + 自定义事件（优先 Vercel 自定义事件；
                          不够用时才建 1 个 ingest 端点 + 1 张 append-only 表）
```

**没有的东西（刻意）**：无 STAGE Core、无注册登录、无微信 OAuth、无回调、无权益系统、无自建 Staff 应用、无 CRM、无支付。Directus 继续纯内容层、永不存学习者 PII（v1 保留的这条边界规则继续有效）。

## 3. 六个问题的直接回答

**Q1 达成当前业务目标的最简架构？**
现站（不动）+ 一个社群引导组件 + 一张企微群活码 + 匿名访客 ID + ≤8 个漏斗事件。新增后端服务数量：**0**（Vercel 自定义事件够用的前提下）；上限 1 个极小端点。

**Q2 v1 蓝图哪些部分推迟？**
STAGE Core 全部（身份、映射表、权益、事件账本服务、Staff RBAC）；微信 OAuth/带参二维码/加群退群回调及其境内回调端点与 ICP 问题（**v1 里最重的基建难题随门禁一起消失了**）；自建 Staff Dashboard 应用；练习数据云同步。全部进入 §6 的触发预案。

**Q3 现在实际需要的最小后端？**
理想为零。仅当 Vercel 自定义事件无法满足（事件量配额/导出需求）时，建：1 个 serverless ingest 路由 + 1 张 Postgres append-only 表（8 字段以内）+ 每周一条聚合 SQL。这是上限，不是起点。

**Q4 现阶段需要向用户收集什么信息？**
网站侧：**什么都不问**（保持零注册、零表单；匿名访客 ID 是随机生成的本地标识，不含任何 PII）。
画像信息（国家/乐器/学位/目标地/申请阶段）在**进群后由运营在对话中自然获得，记为企微标签**。标签体系需要一份 ≤15 个标签的运营手册（B 轨唯一的"数据 schema"），保证日后迁入正式 CRM 时不用重新问一遍。

**Q5 Staff Dashboard v0 包含什么？**
v0 **不是一个应用**，是三样现成工具 + 一页纸：
1. Vercel Analytics（流量、院校/项目页热度、漏斗自定义事件）；
2. 企微控制台（社群人数、增退、标签分布）；
3. **每周一页纸快报**（固定模板，人工 10 分钟汇总）：访客数 → Lab 首练数 → 引导卡曝光/点击 → 本周进群数 → 累计社群规模，加一行"本周结论"。
这页纸就是给广告/合作伙伴谈判用的数据雏形。等它的编制成本或数据量撑不住了（§6 触发），才建自定义看板。

**Q6 如何不阻塞 T 轨前端重建？**
B 轨落入客户端仓库的只有：社群引导卡组件 + 事件埋点（一个 ≤50 行的 `lib/growth/` 模块）。排在 **T3（Lab 重皮）完成之后**作为独立小包（记为 **B1**）实施，与 T1–T7 无文件冲突；照旧需业主批准后才动仓库。在此之前 B 轨全部是仓库外工作（开通企微、建群、写标签手册、配置 Analytics）。

## 4. 漏斗事件词表（v1 冻结，≤8 个）

`visit`（由 Analytics 自带，不用埋）· `lab_first_practice`（首次交卷）· `lab_active_day`（每访客每日一次心跳）· `suite_complete` · `review_opened` · `community_card_shown` · `community_card_click` · `qr_page_view`。
进群数没有回调可自动统计——**由运营每周从企微后台抄录**，与 `community_card_click` 对照即得末段转化率。接受这个精度，这是省掉整个回调基建换来的，划算。

## 6. 预案层：何时把 v1 请回来（触发条件，不进排期）

| 触发 | 启用 |
|---|---|
| 出现**付费功能**（需要区分用户） | Core 身份 + 权益系统（v1 §1–§4 方案直接复用；匿名→账号迁移用现成 history-io 合并，本地数据不丢） |
| 社群 > ~2000 人或人工运营明显过载 | 加群/退群回调 + 半自动化运营（届时才面对境内回调端点问题） |
| 周报编制撑不住或合作方要求数据接口 | Staff Dashboard 自建应用（v1 §3 的 4 页方案） |
| 用户明确要求跨设备同步 | 账号 + 可选云同步 |

**升级时的衔接保证**（现在就守住的三件小事，成本≈0）：匿名访客 ID 生成后不再更换（日后可作为迁移线索）；企微标签严格按手册打（日后可批量导入 CRM）；漏斗事件 payload 带 schemaVersion（沿用全工程既有纪律）。
