# STAGE Staff Platform 战略计划（S 轨 v1）

**日期：** 2026-07-28 · **性质：** 战略计划，非实施规格
**前提：** B 轨已定稿为 v2 精简版（私域获客，Lab 免费，无身份系统）；微信运营细节已剥离至 `docs/ops/WECHAT_PRIVATE_DOMAIN_PLAYBOOK.md`。本文不再讨论微信身份/OAuth/权限/会员。
**与 T 轨关系：** S 轨全部工作在**独立新仓库**进行，与 T 轨（视觉替换 T0–T7）零文件交集、零排期依赖（唯一例外见 §5 B1 说明）。

---

## 1. Staff Platform 应该是什么（Q1）

**裁决：Option C，且其中的"自建部分"采用 Option B 形态（独立内部应用），明确否决 Option A。**

| 选项 | 判定 | 理由 |
|---|---|---|
| A：藏在现有客户站里的仪表盘 | **否决** | 混淆产品边界与流量；扩大客户站安全面；员工鉴权代码污染零注册的客户端；每次 Staff 改动都要走客户站发布——正面违反"内部系统不得影响公开站体验"的既定架构裁决 |
| B：独立内部 Web 应用 | 作为 C 的自建形态 | 独立部署、独立故障域、平台级访问保护 |
| C：现成工具优先 + 后建自定义 | **✅ 采纳** | 三样现成工具已覆盖大半需求：**Directus Insights**（内容运营看板，配置即得，零代码）、**企微控制台**（社群规模与标签分布）、**Vercel Analytics**（流量与院校页热度）。自建只做这三者都做不到的事：漏斗视图、周报生成、社群数字的手工录入 |

**一句话定义：** Staff Platform = 三个现成控制台 + 一个很小的自建应用（`stage-staff`），自建部分只补缺口，永远不复制现成工具已有的界面。

## 2. 部署架构（Q2）

**裁决：新建独立仓库 `stage-staff`（单个 Next.js 应用，内含数据接收端点 + 看板页面），部署为独立 Vercel 项目。**

- **不与 STAGE Front 同仓/同部署**：避免把现仓改造成 monorepo（会搅动正在执行的 T 轨），且发布节奏、故障域、访问控制彻底分离。
- **不自建内网托管**：无办公室基础设施，运维成本不成比例。
- **访问安全（分层，v0 零自建鉴权）**：第一层用 Vercel 平台级保护（团队成员认证/密码保护，随计划能力择一）；若当前计划不支持，退而求其次在应用中间件做一个共享密钥的 Basic Auth（<30 行）。正式的员工账号体系是 §6 触发后的事，现在不建。
- **数据库**：**不碰 Directus 的库**。新开一个独立小型托管 Postgres（如免费档 serverless PG），只存增长事件与手工录入指标。物理隔离比逻辑隔离更省心，成本≈0。
- **已知风险备案**：Vercel 在境内可达性不稳。员工侧访问若成为实际痛点，Staff 应用可整体迁往可达性更好的托管（应用无状态，迁移成本一天以内）；现在不为此增加架构。

## 3. 数据架构（Q3：只定归属与连接，不设计 schema）

| 数据源 | 归属地 | Staff 如何消费 | 现状 |
|---|---|---|---|
| 站点流量/页面热度 | Vercel Analytics | 直接看控制台；不做程序化抽取 | 已可用 |
| 漏斗业务事件（B 轨 §4 的 ≤8 种） | `stage-staff` 自有 Postgres（append-only 一张表） | 本应用直查 + 周聚合视图 | 待 S1 建端点、B1 埋点后产生 |
| IELTS Lab 活动 | **不存在服务端数据**（本地优先是既定架构） | 只能看到漏斗事件级聚合（首练数/活跃日/套题完成），无逐用户数据——这是设计结果，不是缺陷 | 同上 |
| Directus 内容数据 | Directus/PostgreSQL（现状不动） | 内容运营看 Directus Insights；自建应用最多经 Directus API **只读**拉取覆盖度数字用于周报 | 已可用，配置即得 |
| 微信/社群数据 | 企业微信（无 API 接入，B 轨 v2 裁决） | **每周人工录入**：自建应用提供一个极小的手工录入表单（周新增/累计/分群） | 待 S2 |
| 未来支付数据 | 尚不存在 | 仅在事件表设计中预留 `source` 字段维度，不建任何表 | — |

**连接原则：** 全部单向、只读（唯一写路径是漏斗事件 ingest 和手工录入表单）；无 ETL、无数据仓库、无实时管道；聚合用 SQL 视图 + 页面即时查询，数据新鲜度日级即可。事件 payload 带 schemaVersion（全工程既有纪律）。

## 4. MVP 范围：Staff v0 = 4 页 + 1 表单（Q4）

| 页面 | 内容 | 数据来源 |
|---|---|---|
| ① 总览 Overview | 本周关键数：UV（人工周录或链接跳转 Analytics）、Lab 首练、引导卡曝光/点击、本周进群、累计社群规模及趋势线 | 事件表 + 手工录入 |
| ② 增长漏斗 Growth | 访客 → 首练 → 卡点击 → 进群 的周漏斗与周环比 | 事件表 + 手工录入 |
| ③ 内容覆盖 Content | 院校/项目发布数、关键字段缺失计数（截止日/语言要求/学费）——**若 Directus Insights 已覆盖，此页降级为一个跳转链接**（S0 决策点） | Directus API 只读 |
| ④ 周报 Report | 按 `docs/ops` 手册 §6 模板自动拼装本周周报，缺失项留空待人工补，一键复制 Markdown——这就是给广告/合作方的数据底稿生成器 | ①②③ 汇总 |
| ＋ 手工录入表单 | 每周五填：新进群数、累计人数、分群人数 | 写入自有 Postgres |

**明确不做（v0）：** 用户列表/详情（无此数据，也不该有）、实时图表、权限分级、导出 API、任何 CRM 字段。

## 6. 并行执行策略（Q6）

**现在就可并行（T 轨继续跑，互不相扰）：**
- Fable：S0（本文）+ 业主决策收敛
- Opus：S1（独立新仓库，零冲突）→ 接 S2；S1b（Directus 后台配置，不进任何仓库）
- 运营：执行 `docs/ops` 手册 §1–§3（开企微、建群、活码、资料包）——与工程完全无关，今天就能开始
- Codex：S1 完成后做 ingest 端点安全评审（见 §8 说明）；S2 完成后做数据边界评审（确认未触碰 Directus 写路径、无 PII 落库）

**必须等待：**
- B1（客户仓库改动）等 T3 完成 + 业主批准
- 真实数据驱动的漏斗结论等 B1 上线后 2–3 周
- Staff UI 若想复用 T0 的 App family 视觉 token（建议复用，成本低、品牌一致），等 T0 的 token map——**已具备**（T0 已完成），故不构成等待

**回答示例问题：** Staff UI 设计可以在 STAGE Front 重建期间进行吗？——可以，独立仓库 + 已定稿的 T0 token 基线。后端准备可以独立进行吗？——可以，S1 不依赖客户站任何改动。

## 8. 推理强度分级（Q8）

| 阶段 | 强度 | 理由 |
|---|---|---|
| S1 数据落地 | **HIGH** | 唯一涉及安全判断的环节：公网可写的 ingest 端点（滥用防护、速率限制、payload 校验、无 PII 约束）、事件表与保留策略、独立数据库隔离——错了会污染后续所有数据 |
| S1b Insights 配置 | **LOW** | 纯配置、只读面板、可随时重做 |
| S2 Staff v0 | **MEDIUM** | 按已冻结契约装配 4 页 + 1 表单；安全在平台层解决；无架构判断，UI 密度低 |
| B1 埋点+引导卡 | **MEDIUM** | 代码量极小，但发生在客户仓库内、受 T 轨守护约束（不碰机制、guard 必须通过），需要守边界而非高难推理 |
| （不存在 VERY HIGH） | — | S 轨若出现需要 VERY HIGH 的改动（改核心架构），即违反"最小内部平台"约束，应退回本文修订而不是继续实施 |

## 9. 防过度工程（对应约束清单）

不重设计 STAGE Front；不阻塞 T 轨（§5 全表核验）；不建 CRM（画像=企微标签，手册管理）；不建支付；不建复杂鉴权（平台级保护 + 至多 30 行 Basic Auth）；不建企业软件（4 页上限，超出回到 S0 修订）。**S 轨的成功标准：每周五 10 分钟产出一页可信周报，且没有任何员工问"这个内部系统怎么这么复杂"。**
