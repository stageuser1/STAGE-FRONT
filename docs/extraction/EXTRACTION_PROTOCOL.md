# STAGE 院校招生数据抽取规程

> **本文件取代插件版 skill `stage-music-admissions-extractor`。**
> 那一版面向 `stage_music_admissions_v2` 契约与 Directus / Obsidian 产出,两者都已
> 退场:契约现为修订版 v3,产出路径是 OSS 写入 API + draft/publish 分离。冲突时
> **以本文件为准**。本文件是唯一正本;`.claude/skills/` 下的 skill 只做触发与指路,
> 不复制内容(两处各存一份必然漂移 —— 这正是本项目反复踩过的坑)。

本规程写给**没有参与过本项目的会话**(Claude、Codex 或其他)。只读本文件即可独立
执行一所学校的抽取,不依赖任何历史对话记忆。

---

## §0 适用范围与前置

**适用**:把某所音乐院校的官网招生信息,抽取成符合 v3 契约的 canonical 包,并以
draft 状态入库。

**不适用**:发布(`publish`)、数据复核、契约设计、渲染层改动。

### 开工前确认到位

| 项 | 位置 | 用途 |
|---|---|---|
| 契约 schema | `data/contract/stage_music_admissions_v3.schema.json` | 唯一形状标准 |
| 跨校词表 | `data/contract/field-vocabulary.json` | `field_ref` 合法值 |
| 归类先例 | `docs/contracts/field-classification-precedents.md` | `field_category` 怎么判 |
| 校验 CLI | `scripts/oss/validate-package.mjs` | 入库前本地校验 |
| 写入 token | `.env.local` 的 `SCHOOLS_WRITE_TOKEN` | POST 鉴权 |
| 预览 token | `.env.local` 的 `PREVIEW_TOKEN` | 生成复核链接 |
| 风格指南 | `docs/style/CONTENT_STYLE.md` | 中文译名与面向用户的措辞 |

### 术语

- **canonical 包**:一所学校的完整 JSON,契约定义其形状。
- **原子单位**:School × Field × Degree Level。一条 `program_offering` 对应一个原子单位。
- **运营者**:项目所有者。本规程里所有"停下等确认"的对象都是他,不是别的 agent。

## §1 权限边界与硬停点

**这一节放在最前面,因为它是最容易被跳过的一节。** 一个想尽快出活的会话会直接跳到
"怎么抽",于是把本该停的地方跑过去 —— 那时数据已经写进去了。

### 1.1 权限边界(不可协商)

| 你可以 | 你不可以 |
|---|---|
| 抽取、生成包、本地校验 | 发布(`publish`)—— **永远是运营者本人的动作** |
| POST 入库为 **draft** | 把 `status` 写成 `published`(写入 API 会强制改回 draft) |
| 把行级 `review_status` 填 `Extracted` 或 `Needs Review` | 填 `Verified` —— **抽取者不给自己的产出盖章** |
| 报告预览链接、列出待确认项 | 把 `workflow_status.review_status` 翻成 `reviewed` |
| 提出裁决建议 | 替运营者做裁决 |

**为什么这条是硬的**:自评通过等于取消复核。本项目的规则 F 要求实现者的自检不作为
验收依据;抽取同理。你判断"这条我很确定"的时候,恰恰是最需要别人看一眼的时候 ——
本规程 §3 里七条事故,有五条是抽取者当时"很确定"的。

### 1.2 六个硬停点

```
①出抽取计划 ──✋── ②Mode A 专业索引 ──✋── ③Mode B 要求抽取
     ↓
④本地契约校验 ── ⑤POST 入库(draft) ── ⑥报告预览链接 ──✋── 人工复核 ──✋── 运营者 publish
```

| # | 停点 | 停在这里等什么 | 跳过的后果 |
|---|---|---|---|
| ✋1 | 抽取计划之后 | 运营者确认范围、来源页、预计规模 | 抽完才发现范围错,整包重做 |
| ✋2 | Mode A 索引之后 | 运营者确认专业清单、`field_ref`、归类 | 用错误的专业清单抽了几十条要求 |
| ✋3 | 报告预览链接之后 | 运营者逐字段人工复核 | 未复核数据被发布 |
| ✋4 | 复核之后 | **运营者本人**执行 publish | 抽取者越权发布 |

④⑤⑥ 不是停点但**不许乱序**:未过本地校验不许 POST(写入 API 会 422 拒绝,但那是
最后一道网,不是第一道);未 POST 成功不许报告链接。

### 1.3 停下来的正确姿势

停 ≠ 沉默。每个停点交付的东西要让运营者**能直接判断**,而不是让他反过来问你:

- **✋1 抽取计划**:用哪些官网页面(逐个列出真实 URL)、覆盖哪些专业与学位层次、
  预计包规模、**已知的契约装不下的地方**、需要裁决的问题。
- **✋2 Mode A 索引**:专业清单表格,含 `field_ref` / `field_category` / 官方名 /
  专业分页 URL;**判断题单列**并给出你的倾向与理由;排除项与排除理由。
- **✋3 预览报告**:预览链接、包规模、**你做过判断的地方逐条列出**、
  `review_notes` 的要点、待裁决项。

## §2 流程节拍

### Mode A — 专业索引

**产出**:这所学校有哪些专业、各属什么学位层次、`field_ref` 与 `field_category`
怎么定、每个专业的官网分页 URL。

**不做**:任何申请要求、试音要求、费用、日期。

### Mode B — 要求抽取

**产出**:每个专业的申请要求、试音要求、费用、申报门槛、来源记录。

**输入**:✋2 已确认的索引。索引没确认就开始 Mode B,是本规程最常被违反的一条。

### 校验 → 入库 → 报告

```bash
node scripts/oss/validate-package.mjs <包路径>          # 必须 PASS
curl -X POST "$SITE/api/schools" \
  -H "authorization: Bearer $SCHOOLS_WRITE_TOKEN" \
  -H "content-type: application/json" -d @<包路径>      # 期待 200,status 恒为 draft
```

预览链接格式:`$SITE/schools/{school_ref}?preview=$PREVIEW_TOKEN`

## §3 抽取纪律

每条规则的结构统一为四段。**【为什么】开头标注了"(设计意图,非事故沉淀)"的六条,
是从设计推导出来的,情况变了可以挑战;没有此标注的七条是事故沉淀,不要轻易动** ——
它们各自对应一次真实的错误数据,改动前先确认那个坑已经不存在了。

---

### R1 · 反模板化:相同不是默认,是结论

**【规则】** 任何"多条记录的某字段看起来应该相同"的情况,必须**逐条回官网核实之后**
才能填成相同。不许因为"看起来该一样"就复制同一份数据。用脚本批量生成时,共享事实
只写一次是对的,但前提是**那个事实已经逐条核实过**。

**【为什么】** 曾经发生:Berklee 主校抽取时,15 个专业的申请要求与试音要求被复制了
15 份,依据是"Berklee 的试音按主修乐器走、不按专业分"这个**当时未经验证的判断**。
运营者质疑"为什么 15 条曲目和语言要求完全相同",逐项核实后:结论**碰巧是对的**
(录取确实不针对专业),但过程完全不成立 —— 我当时没有任何证据支持它。而顺着这个
质疑往下查,才发现漏掉了整个 `major_declaration_requirements` 维度(见 §4)。

**【后果】** 影响 15 个专业里的 11 个,其中三个是**限额竞争专业**(Electronic
Production and Design、Global Jazz Performance、Music Production and Engineering)。
对用户的伤害很具体:一个中国学生按页面信息判断"考进伯克利就能读音乐制作与工程",
实际上入学后还要过一轮竞争性申请,可能落选。**页面对此只字未提。**

**【判断提示】** 任何"这几条应该一样吧"的念头出现时,问自己:

- 我有**官网原文**支持它们相同,还是只有一个听起来合理的推断?
- 如果它们其实不同,页面会对读者撒什么谎?
- 我是不是因为逐条核实要花 15 次抓取,才觉得它们"应该"相同?

**看起来该相同的时刻,是必须停下核实的时刻,不是可以省事的时刻。**

### R2 · URL 纪律:从索引页取,不拼、不猜

**【规则】** 所有官网 URL 必须来自官网索引页/导航/搜索结果的**实际链接**。不许按
观察到的模式拼接,不许凭常识猜测。拿不到某个专业的分页 URL 时,填已验证的索引页,
**不填未经验证的链接**。

**【为什么】** 曾经发生:抽取 Berklee 学费与音乐治疗专业页时,按"看起来的模式"直接
拼了两个 URL(`/bursar/tuition-and-fees`、`/majors/music-therapy`),**两个都 404**。
更难堪的是,"不猜 URL"这句话就写在我自己那份抽取计划里。改从 `/majors` 索引页一次性
取出全部 15 条权威链接后,顺带发现一处专业名抄错(Film and Media Scoring → 官网
索引页实为 **Film Scoring**)。

**【后果】** 未经验证的链接进包 = 页面上一个点开是 404 的"官网来源"。对一个把
"可溯源"当核心卖点的产品,死链比没有链接更伤 —— 它让所有其他链接都变得可疑。

**【判断提示】** 写下任何 URL 之前问自己:**这个地址我是"看到"的,还是"想出来"的?**
想出来的,一律先访问验证;验证不了就不写。

---

### R3 · 三态区分:肯定 / 否定 / 未提及,是三件事

**【规则】** 对每个"有没有/要不要"类字段,官网只有三种可能:

| 官网情形 | 怎么填 | 怎么记 |
|---|---|---|
| 明确说**有/要求** | 填肯定值 | 附原文引用 |
| 明确说**没有/不要求** | 填否定值(`No` / `Not Required`) | **必须有原句支持** |
| **未提及** | 填 `Unknown` 或 `null` | notes 注明"官网未说明" |

**两个方向都会错**,不要只防一边。

**【为什么】** 曾经发生,一次一个方向:

- **把"未提及"当"否定"**:`prescreening_required` 最初填 `No`,依据是"试音流程页和
  截止日期页描述的完整流程里都没有预筛环节"。独立核对者指出:**官网未明确否定 ≠
  官网说不需要**。改为 `Unknown` + `Needs Review`。
- **把"明确否定"当"未知"**:推荐信 / 简历 / 文书 / 作品集最初一律填 `Unknown`,
  理由是"官网没细说"。交叉核对发现官网 Supporting Materials 页白纸黑字写着
  **"not required to submit supporting materials"** —— 该填 `No`,填 `Unknown`
  是把已经查得到的事实当成了未知。

**【后果】** 前者让用户少准备了一份可能需要的材料;后者让用户白准备了一堆不需要的
材料,并误以为这所学校要求很高。两个方向都在误导决策。

**【判断提示】** 填否定值之前问:**我能引用哪一句原文?** 引不出来就填未知。
填未知之前问:**我是真的查过这一项,还是只是没在主流程页上看到?** 没专门查过就去查。

### R4 · 阶段区分:四件事不能混为一谈

**【规则】** 以下四类要求属于**四个不同阶段**,分别落在不同字段,不许混填:

1. **入学申请要求** → `application_requirements`
2. **入学试音要求** → `audition_requirements`
3. **入学后专业申报门槛** → `program_offerings.major_declaration_requirements`
4. **毕业/修课要求** → **不抽取**(不在本产品范围)

详见 §4。

**【为什么】** 曾经发生:Berklee 的 Performance 专业页有一个标题叫
**"Entrance Requirements"**,底下写的是"See individual requirements for each
instrument"。这句话极易被读成"申报本专业的门槛",实际说的是**入学试音按乐器分设**
—— 而该页对"入学后如何申报 Performance 专业"**只字未提**。第一次读时我差点把它
当成申报门槛填进去。

**【后果】** 把入学试音要求填成申报门槛,会让读者以为"入学后还要再试音一次";
把申报门槛漏掉(R1 的事故),会让读者以为"考进去就能读"。两种都改变申请决策。

**【判断提示】** 读到任何一条要求时,先问:**这是在哪个时间点上要满足的?**
申请时?入学试音时?入学以后?毕业前?标题不作数,以正文原句说的时间点为准 ——
**标题写的和内容说的可能是两件事。**

### R5 · 词表机制:`field_ref` 必须在册

**【规则】** 每个 `field_ref`(`fields[]` 的声明与 `program_offerings[]` 的引用,
两处都算)必须已存在于 `data/contract/field-vocabulary.json`。需要新值时**停下上报**,
走裁决流程 —— 不自造、不"先用着回头再补"。

**【为什么】** 曾经发生:把专业名从 Film and Media Scoring 更正为 Film Scoring 时,
`field_ref` 同步改成了 `film_scoring`,但忘了同步词表就 POST,**生产返回 422**。
这不是 bug,是闸门按设计工作。

**【后果】** 若没有这道闸门:一所学校写 `music_business`、另一所写
`music_management`,浏览页会分裂成两个互不相干的类目,**而且没有任何机制会发现** ——
Directus 退场后词表没有中央归属,这道闸门是唯一的把关点。

**【判断提示】** 想新增 `field_ref` 时问自己:**现有词表里真的没有同义的值吗?**
确实没有,就把它列进 ✋2 的裁决项,由运营者决定 —— 新词进词表是一次显式的、
可审查的 commit,这正是它的价值,不是麻烦。

---

### R6 · 官网自相矛盾:以招生流程页为准,矛盾进 `review_notes`

**【规则】** 同一事实在官网不同页面说法不一致时:以**更权威的页面**(招生流程页 >
专业介绍页 > 宣传页)为准;**把矛盾原样写进 `review_notes`**,含双方原文与出处;
**不擅自调和**,列为待官方确认项。

**【为什么】** 曾经发生:Black Music and Culture 的学位类型 —— `/majors` 索引页
**三次抓取都显示为 Bachelor of Music**,而两个招生页独立称其为 **Bachelor of Arts**。
按规则以招生页为准判为 BA,因本版只做 BM 而排除;矛盾与旁证(搜索摘要称"15 majors
leading to a Bachelor of Music",而索引页列 16 条,减去它正好 15)一并写进
`review_notes`。

**【后果】** 擅自挑一个说法写进去而不留痕,读者拿到的是一个**看起来确定、实际存疑**
的事实;而复核者、下一个抽取者都无从知道这里曾经有分歧。

**【判断提示】** 发现矛盾时问自己:**我是在"判断哪个更可信",还是在"让数据看起来
干净"?** 后者的诱惑很大,因为留矛盾显得工作没做完 —— 但把存疑写成确定,才是真的
没做完。

### R7 · 宁缺毋假:数字逐项回原文,不外推、不取中间值

**【规则】**

- 数字类信息(分数线、费用、学制、日期)**逐项回官网原文定位**,不依赖摘要或记忆;
- 证据不一致时标 `confidence_level: Low`,**不取中间值、不选"看起来对"的那个**;
- 官网未公布的,填 `null` 并在 notes 注明**核实日期**;
- 一个专业有证据、其他专业没有时,**不外推** —— 有证据的填,没证据的留 `null`。

**【为什么】** 曾经发生两件:

- **抓取工具不可靠**:同一个截止日期页两次抓取,给出了**不同的年份**(一次
  "Spring 2027",一次 "Spring 2026")。摘要模型在精确数字上会漂。
- **跨专业外推**:`duration_years=4` 的直接证据只见于 Music Therapy 的学位要求页
  (128 学分 / 八学期),却被填给了全部 15 个专业。交叉核对裁决:9 个有
  "over eight semesters" 直接证据的填 4,其余 6 个**改回 `null`** —— "BM 一般四年"
  是常识,不是这一页给的事实。

**【后果】** 一个错误的截止日期会让人错过申请;一个外推的学制会让人算错预算与签证
时长。数字类错误的伤害是**具体且不可逆**的,与描述性文字不同。

**【判断提示】** 写下任何数字前问:**我现在能指着官网哪一句说"就是它"?** 指不出来
就填 null。以及:**这个数字我是从这个专业的页面上看到的,还是从另一个专业推过来的?**

---

### R8 · Mode A 必须先于 Mode B(设计意图,非事故沉淀)

**【规则】** 先完成专业索引并经运营者确认,再抽取要求。不许合并进行。

**【为什么】**(设计意图,非事故沉淀)"这所学校有哪些专业"和"每个专业要求什么"是
两类不同的判断,依赖不同的页面、不同的证据。合并做时,专业清单的错误会被要求抽取的
工作量掩盖 —— 等发现清单错了,几十条要求已经挂在错误的骨架上。

**【后果】** 用错误的专业清单抽了几十条要求,只能整包重做。

**【判断提示】** 想"顺手把要求也抽了"的时候,问自己:**如果专业清单被推翻,我现在
做的这些要抛掉多少?**

---

### R9 · 硬停点不许跳过(设计意图,非事故沉淀)

**【规则】** §1.2 的四个 ✋ 是硬停,必须等到运营者明确确认才继续。"我先做着,他大概
会同意"不成立。

**【为什么】**(设计意图,非事故沉淀)停点存在的意义是**让错误在便宜的时候被发现**。
计划阶段改范围是改几行字,入库之后改范围是重抽一遍。

**【后果】** 跳过 ✋2 直接抽取,最坏情况是整包作废;跳过 ✋4 自行发布,是越权,且
未复核数据会公开可见。

**【判断提示】** 想继续往下做的时候,问自己:**运营者说过"可以"吗?** 沉默不是同意。

---

### R10 · 契约装不下时,停下上报(设计意图,非事故沉淀)

**【规则】** 遇到契约未预见但真实存在的形状(枚举无对应值、字段无处安放、结构不匹配),
**停下上报请裁决**。不硬塞进最接近的枚举,不静默丢弃。

**【为什么】**(设计意图,非事故沉淀)这是 R3 三态原则在**契约层**的推广:契约没有的
东西,既不是"不存在",也不是"可以随便找个格子放"。Berklee 抽取时遇到过两次并都走了
裁决:`field_category` 8 个值装不下音乐商业/制作工程/音乐治疗等专业(扩了 6 个值);
"入学后申报门槛"无处安放(新增了 `major_declaration_requirements` 字段)。

**【后果】** 硬塞的后果是数据说谎(把"音乐商业"归进"音乐学")。静默丢弃的后果更隐蔽 ——
没有人会知道那个维度曾经存在过,直到用户因此做错决定。

**【判断提示】** 想把一个值塞进"最接近的"枚举时,问自己:**如果用户按这个分类去理解
这个专业,他会误解什么?**

---

### R11 · 范围默认值(设计意图,非事故沉淀)

**【规则】** 第一版只做**本科主流学位路径**。研究生、Diploma / Certificate、Online
项目**默认排除**,除非运营者点名要。排除项与排除理由写进 `schools[].notes`。

**临时约束(见工程待办 B1)**:一个专业当前**只放一条** `application_requirements`
与一条 `audition_requirements`。渲染层适配器不读 `is_current`,取数组首条,放多个
周期会渲染错的那条。**这是迁就渲染层缺陷的临时限制,不是数据模型的本意** ——
`docs/roadmap/ENGINEERING_BACKLOG.md` B1 修复后应删除此约束。

**【为什么】**(设计意图,非事故沉淀)范围默认值让"抽多少"不必每次重新讨论;
临时约束则是显式记账,防止渲染层缺陷通过规程永久化成抽取限制。

**【后果】** 范围失控会让第一版迟迟交不出;而临时约束若不记账,三年后会有人以为
"一个专业只能有一个周期"是产品设计。

**【判断提示】** 想扩范围时问:**运营者点名要了吗?** 想放第二条周期记录时问:
**B1 修好了吗?**

---

### R12 · 权限边界(设计意图,非事故沉淀)

**【规则】** 见 §1.1。终点是 draft;不自评 `Verified`;不翻 `review_status`;
不执行 `publish`。

**【为什么】**(设计意图,非事故沉淀)自评通过等于取消复核。

**【后果】** 未经人工核对的数据公开可见。本产品的错误信息一旦被搜索引擎或大模型
抓取缓存,**撤回也追不回来** —— 这正是 draft/published 分离存在的全部理由。

**【判断提示】** 手要去敲 publish 之前问:**这是我的活吗?** 不是。

---

### R13 · 提交后立即 push(设计意图,非事故沉淀)

**【规则】** 每次 `git commit` 之后立刻 `git push`。见 `CLAUDE.md`。

**【为什么】**(设计意图,非事故沉淀)生产从 `origin/main` 构建。未推送的提交意味着
线上跑的是旧代码,任何"生产实测"的结论都无效。

**【后果】** 本项目为此浪费过两轮排查(详见 `CLAUDE.md`)。

**【判断提示】** 提交完问自己:**推了吗?**

## §4 四个阶段的区分

本轮最大的产品发现,单独成节。美国音乐院校普遍是"**先考进学校、再选专业**",这条
中国学生与家长最容易误解,而它恰好落在四个不同的字段上。

| 阶段 | 时间点 | 字段 | Berklee 实例 |
|---|---|---|---|
| ① 入学申请要求 | 申请学校时 | `application_requirements` | 申请表、$150 申请费、高中成绩单、语言成绩(BM 全校统一) |
| ② 入学试音要求 | 申请学校时 | `audition_requirements` | 自选曲目 3–5 分钟(须现场)、布鲁斯即兴、视奏、听力;**按主修乐器分设,不按专业** |
| ③ 专业申报门槛 | **入学以后** | `program_offerings.major_declaration_requirements` | 11/15 有门槛:先修课、最低 GPA、限额竞争性申请、专业试音 |
| ④ 毕业/修课要求 | 在读期间 | **不抽取** | 128 学分、核心课、通识课 —— 不在本产品范围 |

### 判别方法

读到一条要求时,**只问一个问题:这是在哪个时间点上要满足的?**

- 申请学校时要交/要考的 → ①②
- 已经是这所学校的学生了才谈得上的 → ③
- 讲的是"读完这个专业需要修什么" → ④,不抽

### ③ 的三态(R3 在本字段上的具体应用)

| 官网情形 | `major_declaration_requirements` |
|---|---|
| 明确说明有门槛 | 写入具体条件,**限额/竞争性专业不许压缩成一句话概括** |
| **明确**说无门槛 | 写明"官网明确说明无额外门槛…"(须有原句) |
| **未提及** | `null`,notes 注明"官网未说明" |

`null` 时渲染层整块不显示 —— **绝不显示"暂无要求"**,那会让读者以为可以直接申报,
而事实是我们不知道。

## §5 契约与词表

### 5.1 形状标准

`data/contract/stage_music_admissions_v3.schema.json` 是唯一标准,`additionalProperties:
false`,读写共用同一个校验器。入库前必须本地 PASS:

```bash
node scripts/oss/validate-package.mjs <包路径>
```

### 5.2 词表闸门

`field_ref` 必须在 `data/contract/field-vocabulary.json` 在册,`fields[]` 与
`program_offerings[]` 两处都查。新增走裁决(R5)。词表**只做合法值清单**,不做层级、
别名、翻译。

### 5.3 装不下时

走 R10:停下上报,不硬塞、不丢弃。契约变更由运营者裁决,**单独提交,读写同步**。

### 5.4 包不进仓库

**canonical 包的 JSON 不提交进仓库**,OSS 是唯一真相源。仓库里只放**生成器脚本**
(`scripts/oss/build-<school>-package.mjs`),包本身写到临时目录再 POST。

理由:仓库里放一份包就是第二真相源,它与 OSS 里的那份迟早不一致,而没有任何机制
会发现 —— 与 §5.2 词表要解决的是同一类问题。

### 5.5 用生成器脚本,但要警惕它

重复度高时(多个专业共享校级要求)**用脚本生成而非手写 JSON**:手抄 15 份,抄错一处
就是一条无人发现的错误数据。

**但脚本让"套模板"变得极其容易 —— 它正是 R1 那次事故的温床。** 两件事必须同时成立:

1. 共享事实在脚本里**只写一次**(避免抄写错误);
2. 那个事实**已经逐条核实过是共享的**(避免 R1)。

只做到 1 而没做到 2,脚本就成了批量生产错误数据的工具。

## §6 裁决先例库

已确立的判法,后续同类问题**照判**,不重新发明。

### 6.1 `field_category` 归类

完整先例见 `docs/contracts/field-classification-precedents.md`(五条:制作类不细分、
影视与游戏配乐同类、体裁优先于职能、写作+制作以核心手艺为准、自主设计专业单开类目)。

三处判断题的判法与理由:

| 专业 | 判为 | 理由 |
|---|---|---|
| Contemporary Writing and Production | `Composition/Theory` | 历史根源是编曲写作,制作是载体 |
| Jazz Composition | `Jazz Studies` | 学生的心智入口是"爵士"这个体裁,不是"作曲"这个职能 |
| Professional Music | `Interdisciplinary` | 现有类目无一贴合;并入 `Music Performance` 会失真 |

**不拆 Production/Technology**:三个专业同属制作/工程手艺,拆开会造出单成员类目,
对浏览页分组无益 —— **类目为分组服务,不为分类学服务**。

### 6.2 TOEFL 新旧计分制并存

填**新制值**,旧制写进 `conditional_notes`。(2026-01-21 改版后新制为个位数;
页面呈现问题见工程待办 B2。)

### 6.3 截止日期未公布

`application_deadline` 填 `null`、相关记录 `is_current: false`、`deadline_notes`
注明**核实日期**与官网当时的状态。**不拿过期周期的日期冒充当前周期。**

## §7 交叉核对分工

**抽取者不核自己的产出。**

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 抽取者 | 抽取、入库 draft、报告待确认项 | 不核自己、不发布 |
| 交叉核对者(**另一个独立模型会话**) | 独立读官网原文,逐字段输出 **MATCH / CONFLICT / UNVERIFIABLE** | **不给总体结论**、不改数据 |
| 运营者 | 最终裁决、人工复核、执行 publish | — |

核对者独立读原文,**不读抽取者的结论再去"验证"** —— 那会变成确认偏误。输出只有三态,
不写"整体质量良好"这类总评:总评会掩盖单条 CONFLICT。

Berklee 那轮交叉核对的实际产出:4 处 CONFLICT(推荐信/简历/文书/作品集应为 `No`
而非 `Unknown`)、1 处外推被打回(`duration_years`)、1 处三态纠正
(`prescreening_required` 应为 `Unknown` 而非 `No`)。**这些都是抽取者自评时认为
没问题的字段。**

## §8 交付清单

入库后向运营者报告,包含:

1. **预览链接**:`$SITE/schools/{school_ref}?preview=$PREVIEW_TOKEN`
2. **包规模**:专业数 / 各集合条数 / `review_notes` 条数
3. **你做过判断的地方**,逐条列出(归类判断、译名、三态取舍、矛盾处理)
4. **待裁决项**
5. **公开面门禁自查**:院校页与机读端点应为 404、sitemap 应为 0 条(draft 期间)

### 自查时的计数陷阱

浏览页的设计是**每个 URL 渲染该校全部专业卡片**。所以在预览页 grep 某个标签时,
"出现 11 次"可能完全正常(= 11 个专业有该字段),而不是重复渲染。

不知道这一点会把正常当异常,也可能把异常当正常。**核对某个专业自己那张卡时,
要比较的是"总数是否等于应有该字段的专业数"**,不是"是否只出现一次"。
